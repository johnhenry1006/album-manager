# Database conventions

The API uses PostgreSQL and Prisma. All handwritten runtime, configuration, and seed
code is JavaScript ES modules. The initial single-user schema is documented in
[Schema](SCHEMA.md). Authentication is isolated in the auth module with explicit actor context at
user-specific service boundaries. Favorites are personal; core library data and
background jobs remain shared/identity-independent. See [Auth API](../api/AUTH.md).

## Configuration and client ownership

- The root `.env` is loaded by an absolute path; existing process variables win.
- `DATABASE_URL` takes precedence over `POSTGRES_*`. Use a PostgreSQL URL with a
  database name and percent-encoded credentials. Production should supply it through
  the deployment environment. Never log connection strings or expose them to the browser.
- Without `DATABASE_URL`, configuration uses `POSTGRES_HOST=localhost`,
  `POSTGRES_PORT=5434`, `POSTGRES_DB=album_manager`, `POSTGRES_USER=album_manager`,
  and a required `POSTGRES_PASSWORD`. Containerized APIs use `postgres:5432`.
- CLI and runtime share `src/config/database.js` validation. Generation needs no
  database connection or credentials. Other commands require configured PostgreSQL.
- Only `src/infrastructure/database/client.js` constructs Prisma. The
  `prisma-client-js` generator produces a JavaScript runtime in dependencies; do not
  add a TypeScript generator or build pipeline. Prisma CLI and client versions must match.
- `createDatabase(config)` owns one client/pool per API instance, worker, or script.
  Do not create clients per request, inside repositories, or as import-time globals.
- The server connects and runs `SELECT 1` before serving. Fastify's `onClose` hook
  disconnects once, including startup failure cleanup. Scripts use `try/finally`.
  The PostgreSQL adapter uses a five-second connection acquisition timeout.
- `buildApp({ database })` accepts an explicit owner for tests/composition; omitting
  it builds a database-free instance. Production `startServer()` always supplies one.
- `checkDatabaseHealth(client)` runs a parameter-safe `SELECT 1` and returns
  `{ status: 'ok' }` or `{ status: 'error' }` without exception details. It is an
  operational infrastructure helper, not a business query or a new HTTP endpoint.
  `/api/health` continues to report process liveness.

## Repository boundaries

Application/module composition passes the owned client into repository factories.
Repositories own business queries; services coordinate repositories; controllers
call services. No direct Prisma access from controllers, routes, or domain services.
ESLint restricts Prisma package imports to client infrastructure and prevents
controllers from importing database infrastructure or repositories.

Repository pattern (illustrative; the repository/service is not implemented yet):

```js
export function createAlbumRepository(client) {
    return {
        findById(id) {
            return client.album.findUnique({ where: { id } });
        },
    };
}

// In application/module composition:
// const repository = createAlbumRepository(database.client);
// const service = createAlbumService({ repository });
```

Tests can inject a client substitute. Operations within an interactive transaction
must consume its transaction client rather than fall back to the application client.
Use Prisma query builders or tagged `$queryRaw`; never interpolate untrusted input
into SQL or use unsafe raw-query APIs.

## Schema rules

- **UUID primary keys:** use `id String @id @default(uuid()) @db.Uuid`; foreign keys
  referencing these IDs also use PostgreSQL UUID. Defaults generated by Prisma are
  not database defaults for external SQL writers; document any deliberate change.
- **Timestamps:** persisted entities have `createdAt DateTime @default(now())`
  and `updatedAt DateTime @updatedAt`, mapped to `created_at` and `updated_at`,
  using `@db.Timestamptz(3)`. Store UTC instants. `@updatedAt` is managed by Prisma;
  external writers must explicitly maintain it.
- **Soft deletion where appropriate:** recoverable entities use nullable
  `deletedAt DateTime? @map("deleted_at") @db.Timestamptz(3)`. Repositories exclude
  deleted rows by default and expose deliberate restore/include-deleted operations.
  Define uniqueness, cascades, retention, and permanent cleanup per feature.
  Do not soft-delete transient job/association records without a requirement.
- **Mapping:** use PascalCase model names and camelCase fields in Prisma/JavaScript;
  use plural snake_case table names through `@@map` and snake_case columns through
  `@map`. Map relation foreign-key fields as well.
- **Explicit indexes:** add reviewed `@@index` definitions for actual filters,
  foreign-key joins, sorting, and pagination; PostgreSQL does not automatically index
  referencing foreign-key columns. Unique constraints already provide indexes.
  Avoid redundant/speculative indexes. Document partial/expression indexes in SQL
  migrations when Prisma cannot represent them.
- **Relations:** declare nullability and referential actions explicitly; do not
  cascade-delete original media implicitly. Review deletion behavior per feature.
- **Pagination:** use deterministic ordering with a stable UUID tie-breaker, such
  as `(createdAt, id)`, and an index matching query filters and ordering.

## Commands and migrations

Run from the repository root after `npm ci`:

| Command                                 | Purpose                                    |
| --------------------------------------- | ------------------------------------------ |
| `npm run db:generate`                   | Generate the JavaScript Prisma client      |
| `npm run db:migrate -- --name <change>` | Create/apply a local development migration |
| `npm run db:deploy`                     | Apply committed migrations in deployment   |
| `npm run db:seed`                       | Run the explicit seed entry point          |
| `npm run db:studio`                     | Open Prisma Studio for local inspection    |

The same scripts are available in `@album-manager/api`. Prisma uses
`apps/api/prisma.config.js`, `prisma/schema.prisma`, and `prisma/migrations`.
The initial migration creates the models in [Schema](SCHEMA.md). The lock file fixes
the migration provider to PostgreSQL. Generate after every schema change; Prisma 7
migration commands do not generate the client or seed automatically.

Commit schema changes and reviewed SQL migrations together. Never edit applied
migrations, use `migrate dev` in production, or use `db push` as a deployment path.
Development migration creation needs a disposable shadow database or a local role
allowed to create databases. Deploy with a separate migration role when appropriate.
Do not run migrations automatically on API startup.

The seed foundation verifies connectivity and writes no data. Future seeds must be
explicit, deterministic, idempotent (for example, repository upserts with stable IDs),
and appropriate to their environment. They must not delete existing data by default.
