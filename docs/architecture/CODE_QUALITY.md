# Code quality foundations

Run tooling from the repository root after `npm ci`:

| Command                | Purpose                                                                     |
| ---------------------- | --------------------------------------------------------------------------- |
| `npm run lint`         | Check JavaScript/JSX across workspaces and tooling; warnings fail the check |
| `npm run lint:fix`     | Apply safe ESLint fixes, including import sorting and unused import removal |
| `npm run format`       | Format supported repository files with Prettier                             |
| `npm run format:check` | Check formatting without writing files                                      |
| `npm test`             | Run the scaffold check and Node test runner for tooling tests               |

`eslint.config.js` is the single root ESLint flat configuration. It uses core
recommended JavaScript rules, unused import/variable detection, and consistent
import/export ordering. Browser globals and JSX/React hooks rules apply only to
`apps/web/src`. The backend and repository tooling use Node's recommended ES-module
rules, including built-in import protocol, supported Node APIs, and missing imports.
Shared package code receives neither browser nor Node globals.

Tooling may import root development dependencies. Backend runtime code must
declare its dependencies in `apps/api/package.json`; unpublished dependency checks
remain enabled there. Unused parameters/caught errors may be deliberately named
with a leading underscore; unused imports and ordinary variables remain errors.

Prettier owns formatting; `eslint-config-prettier` disables overlapping formatting
rules. Use two spaces, single quotes in JavaScript, semicolons, trailing commas,
LF endings, and a preferred print width of 100. ESLint and Prettier ignore generated
output, dependencies, runtime media, credentials, and local tool metadata. The root
lockfile is generated by npm and excluded from Prettier.

Import groups, separated by blank lines, are ordered as:

- Side-effect imports.
- Node built-ins using `node:`.
- External packages.
- Workspace-local aliases (`@/` for frontend and `#` for backend).
- Relative imports.

ESLint sorts imports within each group and checks named exports. Prettier does
not reorder imports. React hooks enforce both hook call ordering and exhaustive
dependency arrays. Broader architecture boundaries remain mandatory through the
architecture documents and code review; this foundation does not yet automate
all feature/page import boundaries.

## Aliases

Frontend `apps/web/jsconfig.json` supplies editor navigation for `@/*` → `src/*`.
`apps/web/vite.config.js` supplies the same mapping to Vite at build/runtime.
Examples are `@/app`, `@/pages`, `@/features`, `@/components`, `@/hooks`,
`@/services`, and `@/utils`. Public feature imports must explicitly target
`@/features/<feature>/index.js`. Aliases do not waive architecture boundaries.

Vite is installed only as a build-tool foundation with alias resolution. No HTML
entry point, React runtime, React plugin, app bootstrap, or dev/build command is
provided yet. Future application setup must use the web workspace root/config.
`jsconfig.json` is JavaScript editor configuration, not a TypeScript configuration
or compiler pipeline.

Backend aliases use native Node package `imports` in `apps/api/package.json`:

| Alias               | Target                          |
| ------------------- | ------------------------------- |
| `#modules/*`        | `apps/api/src/modules/*`        |
| `#infrastructure/*` | `apps/api/src/infrastructure/*` |
| `#shared/*`         | `apps/api/src/shared/*`         |
| `#config/*`         | `apps/api/src/config/*`         |

Node requires `#` for native package imports, so backend code uses this supported
syntax instead of `@/`. Include `.js` and explicit `index.js` filenames in backend
local imports; there is no extension inference or custom loader. These aliases
are private to `apps/api` and must not be used from the frontend or shared package.

## Testing scope

Tooling tests in `infrastructure/scripts/code-quality.test.js` check unused imports,
import ordering, hook rules, JSX usage, environment scoping, Node rules, and alias
configuration/resolution. Inline snippets are tooling fixtures, not application
features. A temporary backend alias fixture is cleaned up after the import check.

The root test command also discovers future JavaScript `.test.js` files in the
workspaces with Node's built-in test runner. Browser rendering/hook integration
tests will require a deliberate browser-capable runner when React is introduced.
The current checks are not application tests or proof of application behavior.
